# 验收计划写法

验收项是给**人**看的，不是给测试脚本看的。用户点开页面后，应该能在几分钟内按步骤操作，并判断“过 / 不过 / 阻塞 / 待复测 / 跳过”。

## 条目四要素

每一项至少写清楚：

1. `title`：一个可核对的结果，不写“检查登录”，写“未登录访问 /orders 会跳到登录页并带回跳地址”。
2. `steps`：用户实际要做的 1–5 步，按顺序写；包含入口、账号或数据、关键点击。
3. `expected`：用户能观察到的结果；写页面文案、字段、状态、数量、跳转地址，不写“代码逻辑正确”。
4. `priority`：`P0` 是主流程/阻断上线；`P1` 是重要但可临时绕过；`P2` 是边角、文案、体验。

能提前给测试账号、测试数据、构建号、环境地址的，写在 `note` 里。不要要求用户去猜。

## 章节怎么分

按用户实际验收路径分，不按代码目录分。常见分法：

- `P0 主流程`：从入口到核心结果，3–8 项。
- `P1 异常与边界`：空数据、重复回传、权限不足、超时、回退。
- `P2 显示与兼容`：手机/平板布局、长文案、空状态、错误提示。
- `回归`：上次不通过或改动影响到的旧功能，只放真正需要的项。

一张验收单控制在 15–40 项。超过 40 项时拆成多张验收单，用不同标题和 `sourceTask` 区分；页面支持同频道多张单。

## 状态含义

人工结论只有四档，别再教用户区分六种情况：

| 状态 | 含义 | agent 后续动作 |
| --- | --- | --- |
| `pending` | 还没验，或计划变了要重验 | 等待或提醒验收 |
| `pass` | 按预期通过 | 不需要修 |
| `fail` | 结果不符合预期 | 按实测原因修复，追加 fixLog，再推新版本 |
| `hold` | 这次不验：被阻塞、不适用、暂时跳过 | 报告里如实写“暂缓”和原因，不能当成通过 |

旧值（`untested`/`retest` → `pending`，`block`/`skip` → `hold`）在服务端、CLI 和页面三处都会归并，
历史数据照常显示。计划版本变了以后，已给过结论的条目由页面退回 `pending`，备注保留。

统计口径：`total` / `pending` / `pass` / `fail` / `hold` / `tested`（= total − pending）/
`pct` / `clean`（`pending` 与 `fail` 都为 0 才算收口，`hold` 不阻塞收口但要如实标注）。

## 修复记录怎么写

`item fix` 是只读追加，不改变人工结论。每条写：

- 版本号或构建号；
- 修了什么根因；
- 用户复测时应该看到什么变化。

```text
版本 v1.2.3：空数据时不再白屏，改为显示“暂无订单”空态；复测时清空测试账号订单后刷新首页。
```

不要写“已修复，请测试”这种没有信息量的话。

## 证据怎么放

- 构建成功、接口返回：优先放文字摘要 + 链接；链接要可访问。
- 截图：只在用户需要看视觉差异时放；依赖 image-relay，上传失败就退回文字描述。
- 自动化测试：可以放证据，但不要把自动化通过写成人工已验收；人工结论仍由用户填写。

## 推送时机

- 计划还在编辑时加 `--no-push`，不要每加一项就刷一次页面。
- 计划完整、要交给用户时执行 `connect.mjs`，只发一次链接。
- 用户验收完并自动回传后尽快 `pull`；结果从最后一次回传起保留 10 分钟。
- 修复后重新 `connect`，页面链接不变；计划版本会变，旧结论会提示“计划已更新”。

## 常见错误

- 一项里塞五件事：用户无法判断通过还是失败。拆成多项。
- 预期写“正常”“正确”“符合需求”：不可核对。写成用户能看到的具体结果。
- 把开发自测当成人工验收：页面是给用户做最终确认的，不是 agent 自己点通过。
- 计划里放内部 token、服务器路径、数据库密码：页面链接可能被转发，敏感信息不要进计划。
- 一次验收 80 项：用户会放弃。拆单或只保留本次真正需要人判断的项。
